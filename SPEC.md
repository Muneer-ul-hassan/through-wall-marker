# Wall Marker — build spec (coordinator's contract)

## System in one paragraph
A laptop server takes a drone's video, detects a person with YOLO-Pose,
estimates the person's 3D position, and streams a compact marker (skeleton
joints in the shared world frame + distance + uncertainty + timestamp) to a
phone web page. The phone shows ONLY its own camera feed with the skeleton
overlay — never the drone's video. The shared frame comes from a BRIDGE:
the drone starts beside the phone and flies through the doorway while
keeping visual tracking, so one continuous map chain links the phone frame
to the drone frame. If the bridge is invalid (no bridge / tracking lost),
NO marker is shown — never a guessed position.

## Hard rules (non-negotiable)
1. GROUND / VIRTUAL ONLY. No flight, no motors, no real drone commands.
   Everything is tested on synthetic and recorded video. Real Tello + phone
   test happens later, on the user's go-ahead.
2. Do NOT touch anything outside `wall-marker/` except reading
   `~/workspace/tello-search/tello_path_search.py` (for its --stream-test
   pattern) and `fly_brain.py`. Do NOT touch Drones.zip.
3. iPhone Safari viewer: getUserMedia camera, NO WebXR (Safari has none),
   NO DeviceOrientationEvent use at all (the phone is held still; its pose
   comes from the bridge setup). Full 6-DoF phone tracking on iPhone would
   need a native ARKit app — out of scope; the web viewer is the working
   version. Say so in the README.
4. The phone NEVER receives drone video: no video element, no <img>, no
   fetch of frames. Only compact JSON marker data over SSE. Verify in tests.
5. The marker is a POSE SKELETON (COCO 17 joints, stick figure), never a
   dot. Fallback when pose estimation fails on a frame: hold the last good
   skeleton for at most 0.5 s (flagged stale), then hide it. Never silently
   substitute a dot. Note the choice in the README.
6. NO faked numbers, NO hard-coded answers, NO moved goalposts. If a test
   fails, report the failure with the measured number.

## Coordinate frames and camera models (exact, do not improvise)
- World/shared frame W: origin at the phone's camera centre at session
  start. +X = right from the phone's view, +Y = up, +Z = forward toward
  the wall. Phone pose is FIXED: position (0, 1.5, 0), rotation identity
  (looking +Z). The phone is held still for the whole session.
- Wall plane: z = D_wall (scenario parameter, e.g. 3.0 m). Room B: z > D_wall.
  Person stands on the floor (y = 0), height H (scenario parameter, 1.7 m).
- Drone camera (Tello model, approximate — documented as such):
  W=960, H=720, fx=fy=800, cx=480, cy=360.
- Phone camera (virtual model, approximate — documented as such):
  W=1280, H=720, fx=fy=1000, cx=640, cy=360.
- A 3D point P in world is projected into a camera with world-to-camera
  rotation R and camera centre C (in world coordinates) by:
  p_cam = R @ (P − C); u = fx * x/z + cx; v = cy − fy * y/z.
  Image rows are top-origin (row 0 = top of the frame) while world +Y is
  up, so the row is cy MINUS fy·y/z. (CORRECTED 2026-11-23, second fix:
  an earlier draft wrote v = fy·y/z + cy, which mirrors the image
  vertically — a real upright person maps to an upside-down skeleton,
  ~1.5 m joint error. Verified against real camera rows: a 1.7 m person
  at 4 m projects nose (640, 335.5), ankle (662.5, 713.75) in the
  1280×720 phone model.)
  Cameras are level (no pitch/roll); R is built by a look-at with
  up=(0,1,0), so yaw is the only rotation. Use the P − C form everywhere;
  geometry.project_point takes (K, R, C, P).
  A point behind the camera (z <= 0) projects to nothing.

## Skeleton (COCO 17 keypoints, YOLO-Pose order)
Indices: 0 nose, 1 left_eye, 2 right_eye, 3 left_ear, 4 right_ear,
5 left_shoulder, 6 right_shoulder, 7 left_elbow, 8 right_elbow,
9 left_wrist, 10 right_wrist, 11 left_hip, 12 right_hip,
13 left_knee, 14 right_knee, 15 left_ankle, 16 right_ankle.
Edges (16): (0,1),(0,2),(1,3),(2,4),(5,6),(5,7),(7,9),(6,8),(8,10),
(5,11),(6,12),(11,12),(11,13),(13,15),(12,14),(14,16).
Ground-truth skeleton in person-local coordinates (person height H,
standing, facing the drone): joint heights as fractions of H —
nose .94, eyes .93, ears .93, shoulders .86, elbows .63, wrists .44,
hips .53, knees .29, ankles .05; half-widths in metres for H=1.7 —
shoulders .21, hips .10, elbows .28, wrists .30, knees .09, ankles .09.
Local +x = person's left, +y = up, +z = facing direction. Rotate by the
person's yaw (facing the drone) to get world coordinates.

## Server modules — exact interfaces
### geometry.py
- `PHONE_K`, `DRONE_K`: dicts {fx, fy, cx, cy, width, height}.
- `PHONE_POSE`: (R, C) with R = I(3), C = (0, 1.5, 0) — the phone camera
  centre in world coordinates. Projection uses p_cam = R @ (P − C)
  (see the corrected formula above).
- `project_point(K, R, C, P) -> (u, v, depth) | None` with
  v = cy − fy·y/z (top-origin rows; see the corrected formula above).
- `unproject_ray(K, u, v) -> np.ndarray (3,) unit ray in camera frame`:
  ray = ((u−cx)/fx, (cy−v)/fy, 1), normalised (y-up camera frame).
- `make_transform(R, C) -> 4x4` (world-to-camera: [R | −R@C]; also provide
  `make_transform_from_rt(R, t)` for the standard [R | t] form),
  `invert_transform(T)`, `apply_transform(T, P)`
- `COCO_EDGES`, `COCO_JOINT_NAMES`, `skeleton_local_joints(H) -> (17,3)`.

### detector.py
- `class PoseDetector: __init__(weights="yolov8n-pose.pt", conf=0.5, device="cpu")`
- `detect(frame_bgr) -> list[dict]`, each dict:
  `{"bbox_xyxy": (x1,y1,x2,y2), "conf": float, "keypoints": (17,2) float array
  in pixels, "kpt_conf": (17,) float array}`. COCO class 0 only.
  Empty list when nobody is detected. Must not raise on odd frames.
- `warmup()`: run one dummy inference so the weights download happens once,
  up front, with a clear log line.

### depth.py
- `bbox_height_depth(fx, bbox_h_px, person_h_m=1.7) -> float`
  (Z = fx * H / h). Documented as approximate; error measured in tests.
- `triangulate_point(origins, rays) -> (point (3,), residual_m)`:
  least-squares intersection of >= 2 rays (DLT).
- `estimate_person_depth(history, fx) -> (depth_m, method, sigma_m)` where
  history = list of (drone_pose (R, C), bbox_xyxy, t). If the drone baseline
  (max distance between drone positions in history) >= 0.3 m and >= 2 views:
  triangulate the bbox bottom-centre ray; method="triangulation",
  sigma = max(0.15, residual). Else method="bbox_height",
  sigma = 0.25 * depth. Never return a depth without a method + sigma.
- `joints_3d(kpts_px, kpt_conf, K, drone_pose, depth_m) -> (17,3) in drone
  frame`: drone_pose is (R, C) with C the drone camera centre in world.
  For each joint, ray through (u,v) intersected with the plane
  perpendicular to the drone optical axis at depth_m. Joints with
  kpt_conf < 0.3 are marked invalid (NaN) — the caller must not invent
  them. Document the planar approximation honestly.

### bridge.py
- `class Bridge: __init__()`
- `update(drone_pose_world, tracking_valid, t)`: while tracking_valid, store
  the latest drone pose as the transform (the harness feeds a pose that
  already carries simulated drift; the bridge does not invent drift).
  When tracking_valid is False, call `invalidate()` — permanent until a
  future `reacquire()` (not implemented in the virtual build; document it).
- `state() -> {"valid": bool, "T_world_drone": 4x4 | None,
  "uncertainty_m": float, "age_s": float}`.
  uncertainty_m = 0.10 + 0.02 * seconds_since_start, capped at 1.0 m.
  (A model, not a measurement — the tests check whether real errors stay
  inside the displayed uncertainty.)
- `world_from_drone(T, P)` helper via geometry.

### fusion.py
- `class PersonTrack`: id, pos (3,) world, sigma float, skeleton (17,3)
  world, kpt_conf (17,), last_seen_t, confirm_count, sources set[str].
- `class Fusion: update(drone_id, detections_3d, t)` where each detection
  is {"pos": (3,), "skeleton": (17,3), "sigma": float, "conf": float}.
  Associate to a track if 3D distance < 1.0 m, else create a track.
  Fuse by inverse-variance weighting on pos; per-joint weighted average
  (joints with conf < 0.3 excluded). Track is "confirmed" after 3 updates.
- `marker(t) -> dict | None`: returns the marker JSON (below) only if the
  bridge is valid AND a confirmed track exists with age < 1.0 s. HOLD RULE:
  if the latest update had no usable pose but the track is < 0.5 s old,
  return the last good skeleton with "stale": true. After 0.5 s, None.
  If the bridge is invalid, ALWAYS None. Never a dot.
- Marker JSON (this exact shape, also the SSE payload):
  `{"type": "marker", "person_id": int, "skeleton": [[x,y,z], ...17...],
  "distance_m": float, "uncertainty_m": float, "timestamp": float,
  "stale": bool, "drones": ["drone1", ...]}`.
  Distance = ||pos - phone_position||, phone at (0, 1.5, 0).
  uncertainty = sqrt(track.sigma^2 + bridge.uncertainty^2).

### video_source.py
- `class FrameSource`: `read() -> (frame_bgr, drone_pose, tracking_valid,
  meta) | None`. Implement `FileVideoSource(path, poses_json)` and
  `SyntheticSource(frames)` where frames = list of
  (frame_bgr, drone_pose, tracking_valid, meta) from tests/render.py.
  The real Tello source is a documented stub: raise a clear error
  ("Tello source needs the real drone; use --mode virtual") — do not fake it.

### main.py (CLI + HTTP server, stdlib only — no Flask/FastAPI)
- `python -m server.main --mode virtual --scenario s1_basic --port 8080`
  runs the pipeline on the scenario frames at 10 fps and serves the viewer.
  `--mode live` is the real-run entry: requires djitellopy + a reachable
  Tello; if either is missing it exits with a clear error, never a fake run.
- Routes (ThreadingHTTPServer, bind 0.0.0.0):
  - `GET /` -> 302 to /viewer
  - `GET /viewer` -> phone/viewer.html (text/html)
  - `GET /api/status` -> JSON {bridge_valid, drones, tracks, uptime_s}
  - `GET /api/markers` -> SSE (text/event-stream): `data: <marker JSON>\n\n`
    when a marker exists, otherwise `data: {"type":"none",...}\n\n` at 2 Hz,
    plus `: ping` heartbeat every 5 s. JSON ONLY — no video bytes on any
    route. Only these four routes exist.
- `--https --cert cert.pem --key key.pem` for the iPhone (Safari needs a
  secure context on a LAN IP; plain http works on localhost only).
  Ship `tools/make_cert.sh` (openssl self-signed) and document the
  accept-the-warning step in the README.

## Phone viewer (phone/viewer.html) — exact requirements
- ONE self-contained HTML file, inline CSS/JS, ZERO external resources
  (must work offline on the laptop LAN). No WebXR. No DeviceOrientationEvent
  use at all. Comment in the file: "Phone held still; pose comes from the
  bridge setup (see SPEC.md). No orientation tracking in this build."
- Exactly ONE <video> element: the LOCAL camera via
  `getUserMedia({video: {facingMode: "environment"}, audio: false})`,
  with `autoplay muted playsinline`. Clear on-screen error text if the
  camera is denied/unavailable, and a note that iOS Safari needs HTTPS on
  a LAN IP (or localhost).
- <canvas> overlay on top of the video. EventSource("/api/markers").
  On a marker event: project each skeleton joint with PHONE_K and
  PHONE_POSE; draw COCO_EDGES as lines and joints as small circles (the
  skeleton IS the marker; joints drawn as part of it are fine — a lone dot
  as a marker is not). Draw distance text near the head:
  "≈ X.X m ± Y.Y m". Stale marker: amber colour + "STALE" tag.
- States (big, readable): MARKER (skeleton shown), "No person detected",
  "Tracking lost — marker hidden", "Waiting for server…".
- Reconnect the EventSource automatically on error.
- MUST NOT contain any reference to drone video: no second <video>, no
  <img>, no fetch/XHR to any video endpoint, no "drone" video URL.
  (The harness test greps the file and checks the served routes.)

## Virtual test harness (tests/) — exact requirements
### render.py — synthetic two-room renderer
- Pinhole-camera renderer (numpy + OpenCV only): two rooms, floor with
  procedural checker/noise texture, walls in plaster tones with a skirting
  board and a few rectangular pictures/posters (features for tracking),
  a doorway opening in the shared wall, ceiling. All geometry in world
  coordinates; render from any camera pose with the DRONE_K or PHONE_K model.
- Person billboard: crop ONE standing person from ultralytics' bundled
  `bus.jpg` (locate it via the installed ultralytics package; run the
  detector on bus.jpg and take the largest person detection as the crop).
  Cut the person out with OpenCV grabCut using the bbox, erode the mask
  slightly, and paste as a camera-facing billboard scaled by distance:
  height_px = fy * H / Z. Add a soft contact shadow. If the isolated cutout
  is NOT detected by the pose detector on its own, STOP with a clear setup
  error — do not silently continue with an undetectable person.
- Lighting: a brightness factor per scenario (1.0 normal, 0.5 dim).
- Every rendered frame carries ground truth: person world pos, GT skeleton
  joints in world, GT phone→person distance, GT projected skeleton in the
  phone view, drone pose, tracking_valid flag.

### scenarios.py — the 7 scenarios (60 frames @ 10 fps each)
Drone trajectory (all scenarios): start beside the phone at (0, 1.3, 0.4),
fly to the doorway, through it into room B, hover with small lateral
motion (±0.4 m) so triangulation has a baseline. Drone yaw faces along
motion, then faces the person while hovering.
- s1_basic: person 4.0 m from phone, centred, light 1.0.
- s2_offcentre: person 5.5 m from phone, off to the side near the doorway.
- s3_close: person 3.0 m from phone (just behind the wall).
- s4_dim: light 0.5, person 4.5 m.
- s5_tracking_loss: tracking_valid True until frame 35, False after.
  Person stays visible to the drone the whole time. Marker must vanish
  from frame 36 on and never return.
- s6_no_person: room B empty, same flight path. Zero markers, ever.
- s7_two_drones: two drones, different hover points, both see the person.
  Fused marker asserted; fused error must be <= best single-drone error.

### run_tests.py
- Runs the REAL pipeline in-process (imports detector, depth, bridge,
  fusion from server/) — no mocks of the pipeline itself. Only the video
  frames and poses are simulated (that is the point of virtual testing).
- Per scenario, per frame, record: detection (yes/no), joint errors,
  distance error, skeleton scale error, marker shown (yes/no).
- Metrics per scenario: detection rate, mean + median joint error (cm),
  mean |distance error| (cm), skeleton scale error (%), false markers,
  marker-after-loss count. Print PASS/FAIL per scenario against the
  thresholds below, and write tests/TEST-REPORT.md with the full table,
  the method used per frame (triangulation vs bbox-height), and an honest
  limits section. Exit non-zero if any scenario fails.
- Also run the no-drone-video test: start the HTTP server on a test port,
  GET /viewer (assert exactly one <video> tag, no drone-stream reference),
  read /api/markers events for a few seconds (assert JSON-only payloads,
  no video content-type anywhere), assert no other routes exist.
- PASS thresholds (stated here, do not move them):
  - detection rate >= 0.90 (frames where the person is in the drone view
    and >= 80 px tall)
  - mean joint error <= 0.60 m (primary method)
  - mean |distance error| <= 0.60 m
  - skeleton scale error <= 25%
  - false markers = 0 (s6), marker-after-loss = 0 (s5)
  - s7 fused error <= best single-drone error
